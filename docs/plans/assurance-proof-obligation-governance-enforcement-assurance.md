Exactly three capsules remain authoritative: A owns this assurance model, B implements against it, and C independently executes branch-stage evidence and performs read-only exact-head review. No reviewer, validator, policy manifest, or evidence artifact is a fourth authority surface.

Finite cumulative final-review correction-reentry ceiling: **2 correction-B lineages per accepted A lineage**. One reentry is consumed only by the atomic durable controller-state CAS that publishes a new correction-B grant. A failed-C report may contain multiple mapped findings but consumes one reentry when one correction-B grant is published. Exact replay consumes zero additional reentries. After two successful correction-B grant publications, any later C implementation blocker returns to A.

## Canonical successor wire contracts and validity predicates

This section is the sole V4 wire source of truth. All records use strict canonical JSON: UTF-8 only; no whitespace; object fields in the listed order; integers in the JSON integer grammar with no exponent/fraction and range `0..9223372036854775807` unless stated; booleans lowercase; optional fields omitted, never `null`; and sets sorted by their stated key with no duplicate. Unknown/duplicate/missing required fields, invalid UTF-8, invalid enum, invalid lower-case digest/OID, over-bound value, trailing input, or a semantically false cross-field predicate fails before allocation or authority use. `sha256<T>` is exactly 64 lower-case hex characters and hashes the canonical preimage of `T`; `blob256` hashes exact bytes, not a JSON wrapper; `hexid` is exactly 64 lower-case hex characters but is an assigned identity, not a content digest; `gitOID` is exactly 40 lower-case hex characters. `id` is 1..128 bytes matching `[A-Za-z0-9][A-Za-z0-9._:/-]*`; repository/provider/run/actor identities are 1..1024 bytes; a repository-relative `path` is 1..1024 bytes and rejects absolute paths, `.`/`..`, NUL, backslash and non-normal form; ordinary text is 1..4096 bytes, command text 1..8192, URL 1..2048. New timestamp/deadline fields are canonical UTC RFC3339 seconds exactly `YYYY-MM-DDTHH:MM:SSZ`; existing V1 fields retain their existing validators. Default arrays are 0..256, required sets are 1..256, authority records are at most 1 MiB, retained blobs at most 32 MiB. A content digest is SHA-256 of the listed canonical fields; where a terminal self-digest is named, it is omitted from that preimage and appended last in the sealed form. A reference to `GovernanceActivationV1`, `ControllerStateV1`, `NextStageGrantV1`, `PhaseCheckpointV1`, `LifecycleBindingV1`, `ExecutionBoundsV1`, `ContextCapsuleV3`, `PhaseAuthorityV3`, `PhaseParentV1` or `ledger.Event` means its exact field order, preimage and validator at starting commit `9fc52f81008a98452a2a81c8a6b01bb6aa8c4783`; V4 never reserializes or reinterprets those bytes.

### Exhaustive canonical vector catalog

`CanonicalVectorCatalogV1` is itself `kind,schema_version,descriptor_version="CANONICAL-VECTOR-CATALOG-V1",entries:[]CanonicalVectorEntryV1(set:schema_id),catalog_sha256:self`; an entry is `schema_id:id,record_name:id,positive_recipe="MINIMAL-VALID-V1",rejections:[]CanonicalRejectionVectorV1(set:vector_id)`, and a rejection is `vector_id:text<=512,mutation:text<=128,required_error`. A top-level record's `schema_id` is its exact wire `schema_version`; a nested record's is `nested:` followed by its exact record name. The recipe and mutations generate bytes rather than embedding them, so the finite catalog includes entries for `CanonicalVectorCatalogV1`, `CanonicalVectorEntryV1` and `CanonicalRejectionVectorV1` without recursive vector bytes. The catalog must contain exactly one entry for every top-level and nested record named in this section—no allowlist maintained elsewhere. `AG-VAL-B-015` extracts those names from the immutable A model and rejects missing/extra entries.

Positive bytes are deterministic, not hand-selected by B: the generator uses listed field order; exact constants; first enum value; integer lower bound (or exact value); `"a"` for unconstrained text/id; `"a"*40` for `gitOID`; `"a"*64` for `hexid`/digests; the minimal declared cardinality; lexicographically sorted sets; optional fields omitted; and then applies the record's stated cross-field predicate by repeating the same minimal member/digest where equality/subset is required. It appends/recomputes the self digest where present. The raw `ArtifactBlobV1` positive vector is the single byte `0x61` with size 1 and its real digest; its rejections cover digest/size mismatch, zero length and 32 MiB + 1. For every descriptor constraint the catalog contains a rejection: each required field removed and `null`; each field wrong JSON type; integer below/above bound; string/record/array one byte or item above bound; every enum replaced by `INVALID`; every digest/hexid/OID uppercase, short and bad-character variants; every set unsorted and duplicated; each constant changed; unknown first/last field; duplicate field; invalid UTF-8; trailing JSON; self-digest mismatch; and one named vector for each stated cross-field equality/subset/state predicate. `required_error` is one of `{NON_CANONICAL,UNKNOWN_FIELD,DUPLICATE_FIELD,MISSING_FIELD,TYPE_INVALID,BOUND_INVALID,ENUM_INVALID,DIGEST_INVALID,REFERENCE_TYPE_INVALID,ORDER_INVALID,PREDICATE_INVALID}`. Thus the finite catalog produces positive and rejection vectors for every authority-bearing schema without a second prose source of truth.

Vector naming and mutation are mechanical: `vector_id` is `<schema_id>/<RFC6901-target-or-$>/<mutation-code>` and `mutation` is that final code. The closed codes are `{REMOVE,NULL,WRONG_TYPE,BELOW_MIN,ABOVE_MAX,OVERSIZE,ENUM_INVALID,UPPERCASE,SHORT,BAD_CHAR,UNSORTED,DUPLICATE_MEMBER,CONSTANT_CHANGED,UNKNOWN_FIRST,UNKNOWN_LAST,DUPLICATE_FIELD,INVALID_UTF8,TRAILING_JSON,SELF_DIGEST_MISMATCH,PREDICATE_<frozen-predicate-id>}`. A code performs exactly the single mutation its name states on the generated positive bytes; `WRONG_TYPE` uses `{}` for scalar/array and `false` for object, bound mutations use the adjacent failing integer/item/byte, digest/hex/OID mutations change only the first byte, and unknown/duplicate fields use name `x` and value `0`. `PREDICATE_` changes the lexicographically first participating field to the next individually valid value. The validator rejects any non-mechanical, multi-change or duplicate vector ID.

### Executable validity and drain-before-upgrade

`HistoricalValid(record)` validates immutable canonical bytes and full digest ancestor chain under the schema that created them. `OperationallyUsable(record,state,operation)` additionally requires same repository/controller/A lineage, exact current generation/tip, no invalidation/A-required flag, correct operation, and any existing time-bound lease not expired. Resource/evidence/accounting CAS revisions do **not** invalidate stage authority; only stage/effect transition/invalidation CAS changes stage generation/tip.

`V3Drained(v1,directory)` uses the exact existing V1 vocabulary and is true only when all of these hold under the cutover fence: strict-canonical `ControllerStateV1.Kind=="GovernanceControllerStateV1"`, its `ControllerIdentity`, `RepositoryIdentity` and decoded `Revision=r` equal the selected backend row; `ActiveInvocation==nil`; `FixBatchLeaseSHA256==""`; and the lease tuple is either `(Lease=nil,MutationState=nil)` or a structurally valid historical pair whose `MutationState.LeaseTipSHA256==Lease.LeaseSHA256`, `LeaseStatus==CONSUMED`, and receipt tip validates. Exact live statuses `ISSUED` and `CONSUMING` both fail. A partial lease/mutation pair, mismatched tip, active fix-batch reservation, or active invocation fails. In addition, either no V3 lineage ever started (`BCapsuleSHA256==""`, `CheckpointTip=nil`, `NextStageGrant=nil`, `Derivation=nil`) or the exact checkpoint tip validates as `POST_MERGE_ACCEPTED`; retained review/finding/consumed-lease/grant/derivation bytes are historical only at that terminal tip.

The directory predicate is global, not a fresh host's absence check. `PredecessorAuthorityDirectoryV1` must be sealed and contain every authority-bearing physical identity reachable by the sole authority-domain/controller credential: the workflow row, every bound `ledger.JSONLLedger` plus run ID, the process-startup `ABCP_PR_ADMISSION_ROOT` used by `internal/prlifecycle`, and every `internal/mergelifecycle.Config.StateRoot`. Each binding carries an immutable controller scan artifact. A ledger binding fails drain unless its exact run tip is one of the existing no-outgoing-transition states `{COMPLETED,FAILED,CANCELLED}`; any admitted `.run-locks` operation or `ActiveTransitionBarrier` also fails. A PR binding fails if any exact current V1 revision has `generation`/`submitted` without a valid terminal, or terminal disposition is `remote_diverged_after_write`/otherwise unresolved; success is only the existing `applied_confirmed` or `applied_reconciled`. A merge binding fails if any `target-submission` or target HTTP reservation lacks a validated `target-outcome`/`target-reconciliation` proving the exact existing `applied` or `not_applied` disposition, if `provider_accounting_pending` is true, if its ledger terminal is absent where `applied` requires it, or if any transition barrier is active. Existing `unknown` fails drain. Unknown files, roots, runs, identities or scan truncation fail `V3_DRAIN_REQUIRED`; no caller may assert the directory is complete.

Before cutover, trusted composition rotates/revokes legacy runtime credentials and requires every V1 workflow CAS, ledger transition, PR admission/provider call and merge admission/provider call to register an ACTIVE `PredecessorWriterLeaseV1` and hold the shared PostgreSQL cutover lock for `(authority_domain,controller_identity,writer_epoch)` across its complete state/store/barrier operation. Missing registration fails before mutation. Trusted composition must use `FencedWorkflowAuthorityBackendV1`, which wraps the exact previously selected `WorkflowAuthorityBackendV1`: every V1 CAS obtains the shared writer lease, verifies the directory remains `OPEN` at the bound epoch, performs exactly one underlying CAS, and releases the lease. The wrapped backend identity is immutable in the directory. After `TOMBSTONED`, the wrapper rejects before touching the old backend. This preparation strengthens live V3 admission but does not grandfather a V3 lineage after activation.

The only upgrade operation is one SERIALIZABLE PostgreSQL transaction. It takes the exclusive form of that cutover lock (therefore waiting for all admitted shared writers), locks the successor workflow and directory rows, requires no ACTIVE writer lease, rechecks every registered scan/barrier and `V3Drained`, then—while the exclusive fence still blocks every wrapped V1 CAS—calls the bound underlying V1 backend exactly once to load its current canonical bytes/revision and verifies its immutable backend identity. Those bytes are stable for the remainder of the exclusive fence even when the predecessor backend is not PostgreSQL. In that same PostgreSQL transaction it (1) create-or-verifies an `ArtifactBlobV1` containing those exact bytes, (2) inserts `PredecessorCutoverV1` and changes the directory to `TOMBSTONED`, and (3) replaces the workflow payload with strict `ControllerStateV2` at exactly `r+1`, referencing the exact V1 blob/revision/cutover and `GovernanceActivationV2`. The transaction commit is the single linearization point. Any earlier V1 CAS committed before the exclusive lock and is in the captured bytes; no later V1 CAS/provider admission can acquire the shared fence or pass the tombstone check. Crash before commit leaves V1 OPEN and unchanged; lost commit response is fresh-connection read-back of cutover/V2 exact digests only. Therefore exact V1 bytes are preserved before they cease to be operational, with no live V3 continuation and an exactly empty `grandfathered_v3`.

## Successor activation and immutable artifact authority

`GovernanceActivationV2` installs V4 only from exact existing merge-authorized + post-merge-accepted authority for the policy merge commit, exact installed predecessor activation, authenticated principal and protected base. The controller recomputes the exact five manifest files above. V4 activation additionally requires the directory/fence protocol, `V3Drained`, the same-transaction immutable predecessor artifact/cutover, and the PostgreSQL database-isolation bootstrap below.

Every digest referenced by V2 state/capsules/checkpoints/grants/model/evidence must resolve to its typed immutable blob plus any required occurrence in the same authenticated domain. Blob publication is create-or-verify on digest/size/exact bytes; occurrence publication is a distinct stage/subject/publisher identity. State CAS may reference only committed typed artifacts. A crash between blob commit and occurrence/state CAS leaves a harmless unreferenced blob, not a fabricated occurrence. Fresh hosts traverse ancestors exclusively by typed digests and the shared predecessor directory; host-local absence is never authority.

## Durable publication and remote-effect recovery matrix

| Family | Atomic authority boundary | Crash/ambiguity semantics |
|---|---|---|
| immutable blob/occurrence | blob create-or-verify; separate publisher transaction allocates stage ordinal and inserts occurrence | unreferenced blob is non-authoritative; committed occurrence is never inferred from blob reuse |
| stage close/inventory | one stage-row lock transaction proves zero ACTIVE publishers, changes `OPEN→CLOSED`, and fixes `through_occurrence_ordinal` | commit is the cutoff; later publisher admission/insertion fails; pages/manifest/scan are closure metadata outside the sealed occurrence set |
| stage/checkpoint/grant/evidence selection | expected-revision V2 CAS referencing durable artifact | ambiguous CAS is read-back/reconcile only; no second mutation until exact applied/not-applied proof |
| resource reservation | shared worker-row transaction plus workflow CAS charges the identical full vector and assigns ordinal | no process/container/daemon use before both commits; ambiguous cleanup is `RECOVERY_HOLD` and remains maximum-charged |
| failed stage / correction grant | failed-stage invalidation CAS, then separately derived correction-grant CAS | finding packet alone has zero mutation authority; grant paths are registry-derived |
| PR effect | exact integration event intent → ledger barrier → PG claim → PG call-admission → provider | claim loss before call-admission is provable `NOT_APPLIED`; APPLIED appends READY before PG publication settlement; loss at/after admission is possible-call and reconciliation-only |
| merge effect | exact READY event intent → ledger barrier → PG claim → PG call-admission → provider | same pre-call rule; APPLIED terminal ledger append precedes PG settlement; UNKNOWN retains the barrier |
| post-merge | exact terminal ledger event/evidence then V2 settlement CAS | ledger result remains factual run truth; failed acceptance emits `PostMergeFailureV1`, sets PG non-completion, no automatic rollback |

Raw effect tokens are generated from 256 bits of OS CSPRNG immediately before the winning claim CAS; only SHA-256(token) is durable. The provider adapter accepts an in-memory `OneShotEffectCapability`. `Take()` first verifies the raw token, current claim/request equality, exact active ledger barrier and current PG revision, then CAS-publishes `EffectCallAdmissionV1`; only a confirmed admission lets the adapter cross the transport boundary, and the in-memory object atomically consumes itself. Another host can read the hash but never obtains the capability. An ambiguous admission CAS is read-back only: absent means no call, present means possible call.

The complete PR/merge attempt transition table is closed:

| From | Required durable facts | Only allowed action / linearization | To and crash recovery |
|---|---|---|---|
| no attempt | current admissible ledger event/run/candidate and current PG stage tips | publish typed intent with next permitted ordinal; no provider access | `INTENT_DURABLE`; an orphan intent grants nothing |
| `INTENT_DURABLE` | acquire existing `ledger.AcquireRunTransition(run_id)`, rescan exact bound event, construct exact V1 `TransitionBarrier` commitment | install the existing ledger barrier, then publish `EffectTransitionBarrierV1`; release run lease only after both are confirmed | barrier-only crash: under run lease plus locked PG predecessor, exact-remove/read-back the barrier and publish `EffectBarrierResolutionV1(UNCLAIMED_ABANDONMENT)`; no claim/capability may coexist |
| barrier active | same PG predecessor revision; PR/C invalidation competes on that exact row | one PG CAS installs typed claim, sets coordination `PR_SUBMITTING`/`MERGE_SUBMITTING`, and returns raw-token capability only to winner | `CLAIMED_PRE_CALL`; lost CAS response is read-back, never a second token/claim |
| `CLAIMED_PRE_CALL` | exact claim/barrier/request, no call-admission | live winner may `Take()`; if winner is gone, exclusive PG read proves admission absent and publishes `EffectPreCallClosureV1` | admitted → `CALL_POSSIBLE`; lost winner → settlement `NOT_APPLIED`, then exact barrier resolve/read-back and resolution record |
| `CALL_POSSIBLE` | durable call-admission and matching provider request | at most one transport attempt; persist typed result before settlement | result `APPLIED`, `NOT_APPLIED` or `UNKNOWN`; process loss/timeout/cancel is `UNKNOWN`, read-only reconciliation only |
| `UNKNOWN` | exact result/admission/claim/request and active barrier | append bounded, ordered typed reconciliation observation; zero mutation calls | observation may become `APPLIED` or `NOT_APPLIED`; still unknown CASes coordination to `RECOVERY_REQUIRED` and retains barrier |
| `RECOVERY_REQUIRED` | same ordinal/intention/admission/request and retained exact barrier | append only the next bounded read-only reconciliation; no new intent, capability or mutation call | decisive proof follows the corresponding APPLIED/NOT_APPLIED row; otherwise remain `RECOVERY_REQUIRED` |
| PR `APPLIED` | validated exact PR identity/document/ref observation | using exact barrier append-or-verify `INTEGRATION_ACCEPTED→READY_FOR_MERGE`; reopen/verify event; PG settlement to `PR_PUBLISHED`; exact-resolve/read-back barrier and publish resolution | ledger-first crash settles PG from exact event; PG can never claim PR published without that event |
| PR `NOT_APPLIED` | pre-call closure or provider proof that exact request did not apply | PG settlement CAS to `PR_NOT_APPLIED`, exact-resolve/read-back the barrier, then CAS-publish its resolution record | only after all three facts may `EffectReauthorizationV1` authorize ordinal `n+1` from a newly revalidated integration event/tip |
| merge `APPLIED` | validated exact merge result for request | using exact barrier append-or-verify `READY_FOR_MERGE→MERGED`; reopen/verify event; PG settlement to `MERGE_APPLIED`; exact-resolve/read-back barrier and publish resolution | ledger-first crash settles PG from exact event; PG can never claim APPLIED without that event |
| merge `NOT_APPLIED` | pre-call closure or authenticated provider proof | PG settlement CAS to `MERGE_NOT_APPLIED`, exact-resolve/read-back barrier and publish resolution | ledger remains READY; only `EffectReauthorizationV1` plus resolution and revalidated READY/tips permits ordinal `n+1` |
| settled `APPLIED` or `NOT_APPLIED` | exact byte-identical terminal settlement | create-or-verify/read only | conflicting result, request digest, ordinal, winner or settlement is integrity failure; APPLIED always wins over cancellation |

Within one attempt, `provider_request_sha256` is identical—not merely semantically equivalent—in intent, barrier commitment, claim, call admission, every result/reconciliation, settlement and barrier resolution; reauthorization repeats it as `prior_provider_request_sha256`, while its distinct `new_provider_request_sha256` must equal the next ordinal's intent. `pr_request_sha256` is removed from V4. A result/reconciliation artifact cannot settle a different request, run, ledger event, claim or ordinal. A new ordinal never revives the old capability and is forbidden from `APPLIED`, `UNKNOWN` or `RECOVERY_REQUIRED`.

Barrier removal has one frozen cross-store recovery order. The resolver holds `AcquireRunTransition` and the locked PG effect row, verifies either an exact `RESOLVE` settlement or the unclaimed predecessor, calls the existing idempotent `ResolveTransitionBarrier`, reopens the ledger to prove that exact barrier absent, then commits `EffectBarrierResolutionV1`. Ledger deletion is the removal linearization point. Crash before it leaves the barrier active; crash after deletion but before the PG record can only repeat absence verification and the same resolution CAS. The PG row lock excludes a new claim during an unclaimed removal, and provider admission independently requires the exact active barrier, so no crash gap can convert removal into a provider call.

## Frozen resource authority

Validator authority—not the caller—binds the exact `ResourceProfileV1` digest, secret capability, network policy and container/daemon requirements. No “equal or stronger” caller substitution exists: a reservation repeats the exact profile digest and every numeric reserved field must be greater than or equal to that profile while remaining within its parent/lineage maxima. The worker coordinator is a shared PostgreSQL authority keyed by immutable worker identity, outside any one workflow row. Its security-definer admission/release functions lock the worker row and atomically sum every non-`RELEASED` reservation across authority domains/controllers/lineages. Direct reservation-table DML is revoked. A per-workflow CAS may reference the shared reservation only after it commits; if workflow CAS fails, the reservation remains `RECOVERY_HOLD` until exact absence permits release.

Worker capacity is 12 GiB total reserved memory across process+containers+Docker daemon, 384 total PIDs, 6 CPU equivalents (`600000/100000`), 4096 aggregate NOFILE, 4 GiB cache, 2 GiB container tmpfs, 256 MiB shm, 64 MiB logs and 2 GiB immutable image-cache charge. Devagent preflight additionally requires ≥8 logical CPUs and ≥16 GiB physical RAM. `WorkerCapacityReservationV1` binds worker/domain/controller/repository/A-lineage, owning invocation/cell, parent, exact profile, every process/container/cache/log/image/daemon counter, lifecycle and release evidence. `RESERVED|RUNNING|SETTLING|RECOVERY_HOLD` all count at reservation maxima; only an atomic `RELEASED` transition after cgroup/process/container absence and evidence durability subtracts them. Restart, another controller, another workflow or another domain cannot obtain an independent capacity total.

## Evidence and secret inventory authority

Every attempt first commits the shared `WorkerCapacityReservationV1` and workflow `AssuranceResourceReservationV1`, then opens an `ArtifactPublisherReservationV1`. Execution emits its identity/evidence/resource blobs and publishes a distinct occurrence for every retained PASS/FAIL/VALIDATION_UNAVAILABLE/unselected/orphan stage artifact—even when two occurrences reuse identical bytes. The stage/subject row, not a global sequence, assigns contiguous commit-ordered ordinals. Stage close is one transaction that excludes new publishers, requires zero ACTIVE publisher reservation and fixes the cutoff; a publisher that may still commit therefore prevents close. The controller reads exactly ordinal `1..cutoff`, rejects gaps/duplicates, builds at most 16 pages of at most 128 entries, verifies the domain-separated Merkle root, and thus covers the full 2,048-occurrence ceiling.

Inventory pages/manifest, scan authority/evidence and `StageClosureV1` are generated only after the occurrence set is CLOSED. They are immutable closure blobs, not members of the occurrence set they describe. The inventory manifest enumerates its pages, the scan authority enumerates the manifest/pages as `closure_metadata_sha256s`, and the final closure enumerates those records while excluding its own digest. This exact layering removes self-reference; only OPEN-stage retained artifacts are claimed as complete occurrences. Unreferenced blobs have no stage occurrence and cannot satisfy evidence, while a blob from an abandoned attempt still has its explicit ORPHAN occurrence if it was retained before close.

The controller registers every acquired/generated credential under `(lineage,stage,stage_subject,secret_id,capability,acquisition identity)` before its first use. `StageSecretSetV1` is controller-owned; each `value_commitment_sha256` is SHA-256 of `"ABCP-SECRET-V1" NUL commitment_nonce NUL secret_id NUL decimal_length NUL exact_secret_bytes`. At closure, after ordinary publishers finalize, the controller seals that complete set, derives candidate diff bytes from exact subject base/candidate OIDs into quarantine, hashes `CandidateDiffArtifactV1`, and performs a preliminary full-set zero-match scan of the diff. Only zero-match allows the controller's final publisher to commit the diff blob/occurrence and finalize; a match retains only digest/size incident metadata and the stage fails without closing PASS. The stage then closes, and the final scan streams every sealed occurrence blob exactly once, necessarily including the retained candidate-diff occurrence. The scanner receives the complete exact secret values and nonce over controller FD3 frames, recomputes the commitment/count, and fails if the FD set differs from `StageSecretSetV1`. `SecretScanEvidenceV2` repeats the exact stage subject, secret-set commitment, candidate-diff digest and sealed inventory. A positive match or any missing credential/diff/blob/page/count prevents PASS and stores only redacted `SecretEgressIncidentV1`; offending raw bytes/raw output are never inserted.

Real upstream provider credentials never enter the Codex process, repository, child environment, argv, config file or evidence. J-05 starts a controller-owned loopback-only `CodexProviderBrokerV1` whose entire provider contract is the canonical `CODEX_BROKER_V1` vector: derived base URL `http://127.0.0.1:<reservation-owned-port>/v1`; only `POST /responses` and `POST /responses/compact`; 900,000 ms token TTL, at most five renewals, 32 requests/token and 128/session, 8 MiB aggregate request and 256 MiB response bytes; connect/request/stream-idle/session timeouts 5,000/300,000/60,000/5,400,000 ms; zero transport retry and zero stream reconnect. Codex 0.149.0 uses `model_provider="abcp-broker"`, `env_key="ABCP_BROKER_SESSION_TOKEN"`, `wire_api="responses"`, `requires_openai_auth=false`. Each 256-bit session token is bound to exact reservation/execution/tool/model/budgets; renewal atomically invalidates the old token. `shell_environment_policy.exclude=["ABCP_BROKER_SESSION_TOKEN"]` is mandatory.

Before any real broker session, the exact Codex sandbox/config runs harmless-sentinel probes proving (a) token-name absence from tool-shell environment, (b) a tool subprocess cannot read a same-shaped marker from the Codex parent environment/proc view, and (c) a tool subprocess cannot connect to the broker loopback endpoint while the Codex client can. Any readable marker, reachable tool connection, inability to prove the parent-process boundary, provider/config/route drift or probe ambiguity is `VALIDATION_UNAVAILABLE`; no real provider credential/session starts. The broker rejects non-loopback clients, wrong/expired/replayed tokens, unbound models, budget overflow and non-allowlisted routes; strips inbound authorization before injecting upstream credentials; never follows redirects or uses proxies; closes a stream at idle/total timeout; and never logs credential/token/header/body bytes.

PostgreSQL/Docker passwords are controller-generated into 0400 files in an ephemeral 0700 directory outside repo/evidence roots; Docker receives only `POSTGRES_PASSWORD_FILE=/run/secrets/postgres_password` and a read-only bind of that file. Secret-capable process raw stdout/stderr is scanned in bounded memory and discarded; only structured secret-free results are retained. Exact secret values (including the broker session token and upstream credential inside the controller boundary) are delivered to `assurance-secret-scan.py` over controller-owned FD3 length frames, never argv/env/file evidence.

A credential-bearing stage cannot publish its evidence-selection checkpoint until its complete inventory and matching stage-local PO-041/PO-052 zero-match scan are PASS. B, C, integration and post-merge each have such cells.

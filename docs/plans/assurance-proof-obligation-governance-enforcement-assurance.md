After two successful correction-B grant publications, any later C implementation blocker returns to A.

## Canonical successor wire contracts and validity predicates

This section is the sole V4 wire source of truth. All records use strict canonical JSON: UTF-8 only; no whitespace; object fields in the listed order; integers in the JSON integer grammar with no exponent/fraction; booleans lowercase; optional fields omitted, never `null`; and sets sorted by their stated key with no duplicate. Unknown/duplicate/missing required fields, invalid UTF-8, invalid enum, invalid lower-case digest/OID, over-bound value, trailing input, or a semantically false cross-field predicate fails before allocation or authority use. `sha256<T>` is exactly 64 lower-case hex characters and hashes the canonical preimage of `T`; `blob256` hashes exact bytes, not a JSON wrapper; `hexid` is exactly 64 lower-case hex characters but is an assigned identity, not a content digest; `gitOID` is exactly 40 lower-case hex characters. `id` is 1..128 bytes matching `[A-Za-z0-9][A-Za-z0-9._:/-]*`; `identity` is 1..1024 bytes; `branch` is 1..255 UTF-8 bytes accepted by `git check-ref-format --branch`; `ref` is 6..1024 bytes, starts `refs/`, and passes `git check-ref-format`; `origin` is a normalized `https://host[:port]` value of 1..2048 bytes with no userinfo/path/query/fragment; `routeTemplate` is an absolute ASCII path template of 1..2048 bytes with only literal segments plus named `{field}` segments and no scheme/host/query/fragment; `route` is an absolute percent-escaped path of 1..2048 bytes with no scheme/host/query/fragment; `query` is 0..4096 ASCII bytes in canonical `url.Values.Encode` order; `prTitle` is 1..1024 UTF-8 bytes and `prBody` is 0..1024 UTF-8 bytes, both already trimmed, single-line and free of Unicode control code points; a repository-relative `path` is 1..1024 bytes and rejects absolute paths, `.`/`..`, NUL, backslash and non-normal form; ordinary `text` is 1..4096 bytes; `document` is 0..65536 bytes; command text is 1..8192 bytes; URL is 1..2048 bytes; `u64` is `0..9223372036854775807`. New timestamp/deadline fields are canonical UTC RFC3339 seconds exactly `YYYY-MM-DDTHH:MM:SSZ`; existing V1 fields retain their existing validators. An array written `[]T(order|set,min..max)` has that exact cardinality; no implicit array bound exists. Authority records are at most 1 MiB and retained blobs at most 32 MiB. ### Exhaustive canonical vector catalog

`CanonicalVectorCatalogV1` is itself `kind,schema_version,descriptor_version="CANONICAL-VECTOR-CATALOG-V2",entries:[]CanonicalVectorEntryV1(set:schema_id,1..256),catalog_sha256:self`; an entry is `schema_id:id,record_name:id,fields:[]WireFieldDescriptorV1(order,1..256),predicates:[]PredicateDescriptorV1(set:predicate_id,0..256),positive_recipe="MINIMAL-VALID-V2",rejections:[]CanonicalRejectionVectorV1(set:vector_id,1..4096)`, a predicate is `predicate_id:id,schema_id:id,field_paths:[]text(set,1..64),operator:{ALL_EQUAL,EXACT_LITERAL,IF_AND_ONLY_IF,IMPLIES,EXACTLY_ONE,SUBSET,ORDINAL_SUCCESSOR,STATE_TRANSITION,TYPED_REFERENCE,DIGEST_PREIMAGE,DERIVATION,AGGREGATE_LEQ},arguments:[]text(order,0..64),required_error="PREDICATE_INVALID"`, and a rejection is `vector_id:text<=512,mutation:text<=128,required_error`. Predicate enumeration is total and stable. Literal, optional-arm, equality, typed-reference, self-digest, derivation and state clauses written inline produce IDs `P-<schema-id>-<OPERATOR>-<first-field-path>`; collision suffix is the one-based field-order ordinal. Each retained unlabelled cross-field clause in a row is assigned `P-<schema-id>-ROW-<NNN>`, where NNN is its one-based left-to-right semicolon clause ordinal after code-span-aware splitting. Referenced field paths are the field tokens named in that clause, sorted by descriptor ordinal; if none is named, the sole path is `$` for the complete record. Operator selection is the first matching token in this frozen precedence: `sum→AGGREGATE_LEQ`, `transition→STATE_TRANSITION`, `successor/ordinal→ORDINAL_SUCCESSOR`, `subset/narrow→SUBSET`, `exactly one→EXACTLY_ONE`, `iff/if and only if→IF_AND_ONLY_IF`, `requires/only/when→IMPLIES`, `digest/hash→DIGEST_PREIMAGE`, `reference/target/type→TYPED_REFERENCE`, `equal/match/repeat→ALL_EQUAL`, otherwise `DERIVATION`; arguments are the exact normalized clause bytes. Before cutover, trusted composition rotates/revokes legacy runtime credentials and requires every V1 workflow CAS, ledger transition, PR admission/provider call and merge admission/provider call to register an ACTIVE `PredecessorWriterLeaseV1` and hold the shared PostgreSQL cutover lock for `(authority_domain,controller_identity,writer_epoch)` across its complete state/store/barrier operation. Missing registration fails before mutation. Trusted composition must use `FencedWorkflowAuthorityBackendV1`, which wraps the exact previously selected `WorkflowAuthorityBackendV1`: every V1 CAS obtains the shared writer lease, verifies the directory remains `OPEN` at the bound epoch, performs exactly one underlying CAS, and releases the lease. The wrapped backend identity is immutable in the directory. After `TOMBSTONED`, the wrapper rejects before touching the old backend. This preparation strengthens live V3 admission but does not grandfather a V3 lineage after activation.

The only upgrade operation is one SERIALIZABLE PostgreSQL transaction. It takes the exclusive form of that cutover lock (therefore waiting for all admitted shared writers), locks the successor workflow and directory rows, requires no ACTIVE writer lease, rechecks every registered scan/barrier and `V3Drained`, then—while the exclusive fence still blocks every wrapped V1 CAS—calls the bound underlying V1 backend exactly once to load its current canonical bytes/revision and verifies its immutable backend identity. Those bytes are stable for the remainder of the exclusive fence even when the predecessor backend is not PostgreSQL. In that same PostgreSQL transaction it (1) create-or-verifies an `ArtifactBlobV1` containing those exact bytes, (2) inserts `PredecessorCutoverV1` and changes the directory to `TOMBSTONED`, and (3) replaces the workflow payload with strict `ControllerStateV2` at exactly `r+1`, referencing the exact V1 blob/revision/cutover and `GovernanceActivationV2`. The transaction commit is the single linearization point. Any earlier V1 CAS committed before the exclusive lock and is in the captured bytes; no later V1 CAS/provider admission can acquire the shared fence or pass the tombstone check. Crash before commit leaves V1 OPEN and unchanged; lost commit response is fresh-connection read-back of cutover/V2 exact digests only. Therefore exact V1 bytes are preserved before they cease to be operational, with no live V3 continuation and an exactly empty `grandfathered_v3`.

## Successor activation and immutable artifact authority

`GovernanceActivationV2` installs V4 only from exact existing merge-authorized + post-merge-accepted authority for the policy merge commit, exact installed predecessor activation, authenticated principal and protected base. The controller recomputes the exact five manifest files above. V4 activation additionally requires the directory/fence protocol, `V3Drained`, the same-transaction immutable predecessor artifact/cutover, and the PostgreSQL database-isolation bootstrap below.

Every digest referenced by V2 state/capsules/checkpoints/grants/model/evidence must resolve to its typed immutable blob plus any required occurrence in the same authenticated domain. Fresh hosts traverse ancestors exclusively by typed digests and the shared predecessor directory; host-local absence is never authority.

Within one attempt, `provider_request_sha256` is the effect-specific `PREffectRequestV1` or `MergeEffectRequestV1` digest and is identical—not merely semantically equivalent—in intent, typed barrier commitment, claim, call admission, every result/reconciliation, settlement and barrier resolution; reauthorization repeats it as prior/new typed requests. The generic `ProviderRequestV1` is only the raw transport child and grants no authority by itself. A result/reconciliation artifact cannot settle a different principal, repository, document, PR, ref, request, run, ledger event, claim or ordinal. A new ordinal never revives the old capability and is forbidden from `APPLIED`, `UNKNOWN` or `RECOVERY_REQUIRED`.

Barrier removal has one frozen cross-store recovery order. The resolver holds `AcquireRunTransition` and the locked PG effect row, builds `EffectBarrierRemovalProofV1` from either an exact same-chain `RESOLVE` settlement or exact `EffectUnclaimedAbandonmentV1`, and calls only `ledger.ResolveEffectBarrierV4(barrier,proof,coordinationVerifier)`. The ledger boundary decodes the embedded commitment, validates the typed proof and exact current source/authorized APPLIED terminal event as applicable, rejects any competing FAILED/CANCELLED/other terminal, removes only that barrier, then the controller reopens the ledger to prove absence and commits `EffectBarrierResolutionV1`. Ledger deletion is the removal linearization point. Crash before it leaves the barrier active; crash after deletion but before the PG record can only repeat absence verification and the same resolution CAS. The PG row lock excludes a new claim during unclaimed removal, and provider admission independently requires the active typed barrier plus exact source event under the run lease.

At the ledger mutation boundary, an active `EffectLedgerBarrierV4` makes existing `Append`, `AppendOrVerify`, `AppendOrVerifyLeased`, legacy `AppendOrVerifyTransition` and legacy `ResolveTransitionBarrier` all fail closed regardless of any supplied digest or terminal state. Only `AppendOrVerifyEffectTransitionV4(event,authority)` may append, and it independently re-parses the current source line, barrier, commitment, outcome and deterministic event bytes while holding the run lock. Only `ResolveEffectBarrierV4` may remove. Thus FAILED, CANCELLED, a different APPLIED event, a byte-valid event from a different run/ordinal/kind and the legacy “any terminal” path cannot cross an active V4 barrier.

## Frozen resource authority

Validator authority—not the caller—binds exactly one `MaterializedResourceProfileV1` digest containing the complete flattened process, output, cache, container, image, Docker-daemon, secret and network vector. Component names in the registry are derivation inputs only: `SECRET_CAPABLE_V1 + POSTGRES_CONTAINER_V1` and `DOGFOOD_V1 + POSTGRES_CONTAINER_V1` must materialize their checked union before authority issuance; no validator/reservation may carry two independent selectable profiles. No “equal or stronger” caller substitution exists: execution and both reservations repeat the exact materialized digest and every numeric reserved field equals that profile, except an inclusive J-05 parent may reserve the larger frozen child ceiling. The worker coordinator is a shared PostgreSQL authority keyed by immutable worker identity, outside any one workflow row. Its security-definer admission/release functions lock the worker row and apply the exact root/suballocation predicates below across authority domains/controllers/lineages. Direct reservation-table DML is revoked. A per-workflow CAS may reference the shared reservation only after it commits; if workflow CAS fails, the reservation remains `RECOVERY_HOLD` until exact absence permits release.

Worker capacity predicates are executable checked-u64 inequalities over every non-RELEASED root reservation and the exact same-named `WorkerCapacityV1` fields: `Σ(process_memory+container_memory+unique_daemon_memory)≤aggregate_memory_bytes=12884901888`; `Σ(process_pids+container_pids+unique_daemon_pids)≤aggregate_pids=384`; `Σ(process_cpu+container_cpu+unique_daemon_cpu)≤aggregate_cpu_micros_per_period=600000` with every nonzero period equal `aggregate_cpu_period_micros=100000`; `Σ(nofile)≤4096`; `Σ(cache+container_image+unique_daemon_cache)≤combined_cache_image_daemon_bytes=4294967296`; `Σ(container_tmpfs)≤2147483648`; `Σ(container_shm)≤268435456`; `Σ(container_log+unique_daemon_log)≤67108864`; and `Σ(container_image)≤2147483648`. Admission strict-parses and digest-validates that capacity record before using any number; a host-discovered larger value cannot replace it. “Unique daemon” means one exact `(daemon_capacity_sha256,image_digest,docker_root_identity)` charge with a locked refcount; conflicting identity is rejection. Nesting uses inclusive suballocation. A row with no parent is `ROOT_CHARGE` and alone contributes its whole vector to the worker sums. A depth-1 J-05 child is `INCLUSIVE_CHILD_SUBALLOCATION`: it contributes zero additional worker-root charge, must name the exact active parent, and each child dimension is `≤` the corresponding parent dimension. Under the same worker lock, for every active parent and every dimension, `parent_direct_actual_or_reserved + Σ(active child reserved) ≤ parent reserved`; therefore siblings cannot oversubscribe and child reservations consume, rather than duplicate, the parent allocation. Parent release is forbidden while any child is non-RELEASED, child lineage/worker/domain must equal its delegation binding, nesting depth is exactly 1, and no child can be a parent. Resource evidence reconciles child actuals into the parent's inclusive usage before either release. Restart, another controller, another workflow or another domain cannot obtain an independent total.

## PostgreSQL authority-domain and artifact backend

Implementation is `PostgresWorkflowAuthorityBackendV1` under `internal/authoritybackend/**` with `github.com/jackc/pgx/v5 v5.7.6` (Go 1.23 compatible). Schema is fixed `abcp_v4`. Bootstrap creates four exact NOLOGIN roles—`abcp_v4_schema_owner`, `abcp_v4_runtime`, `abcp_v4_domain_fn`, `abcp_v4_worker_fn`—all `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`; `abcp_v4_schema_owner` owns schema/tables only and owns no function, while the two `_fn` roles own only their named functions and own no schema/table. Per-domain runtime roles are LOGIN with those same negative attributes and membership only in `abcp_v4_runtime`; they have no membership or SET ROLE path to any owner role. Each `bytea` argument is one strict canonical request record of the corresponding named V1 operation, limited to 1 MiB, and each function returns one strict canonical result record as `bytea`; no scalar domain/identity override exists. Each is SECURITY DEFINER with `SET search_path=pg_catalog,abcp_v4` and `SET row_security=on`, contains no dynamic SQL, first verifies `session_user` maps to exactly one requested authority domain, verifies `current_user` is its exact function-owner role, and never accepts caller/domain/role names as SQL identifiers. Only `abcp_v4_runtime` receives EXECUTE; PUBLIC and each individual login have no direct EXECUTE grant. The worker function's explicit `USING (true)` SELECT policies intentionally expose cross-domain capacity totals only to its NOLOGIN owner; its frozen body returns no foreign row or identifier, while INSERT/UPDATE remains RLS-constrained to the validated `session_user` domain. Bootstrap validates role attributes, ownership, memberships, function bodies/config/owners, table grants, EXECUTE grants, all policy expressions and every FORCE flag on every open; any drift fails before state access.

`abcp_worker_reserve_v1` takes `FOR UPDATE` on the one worker-capacity row, verifies canonical bytes/digest/profile/worker/domain/lineage/owner/parent identity, parses every frozen numeric field with checked `u64` arithmetic, and sums every reservation whose lifecycle is not `RELEASED`. The three CPU periods must all be 100000; compatible image/daemon charges are keyed and refcounted once, while conflicting identities fail. It inserts only if every independent process/container/tmpfs/shm/cache/log/image/daemon sum remains within `WorkerCapacityV1`. `abcp_worker_release_v1` takes the same row lock and changes exactly `SETTLING→RELEASED` only after exact `ResourceEvidenceV1`, container/cgroup/process absence and durable stage evidence; ambiguity leaves `RECOVERY_HOLD` fully charged. This worker-row lock is the aggregate admission/release linearization point across all domains, controllers and workflows.

Bootstrap registers the exact predecessor directory but cannot install V2. Only `abcp_cutover_v1` performs the fenced same-transaction V1 blob/tombstone/V2 `r+1` operation; it never inserts revision 1 blindly. Blob create-or-verify uses `INSERT ... ON CONFLICT DO NOTHING` followed by same-transaction SELECT and application SHA/size/byte equality.

Publisher functions use one immutable lock order: exact stage row `FOR UPDATE`, then exact publisher row `FOR UPDATE` where it exists. `abcp_publisher_open_v1` locks/checks OPEN plus expected stage revision and inserts/create-or-verifies the reservation as ACTIVE in that transaction, so it cannot race close. `abcp_publisher_append_v1` locks both, requires OPEN+ACTIVE and exact owner/stage/subject/reservation, allocates the stage's next ordinal, inserts one occurrence and advances ordinal/revisions. `abcp_publisher_finalize_v1` locks both and CASes ACTIVE→FINALIZED, optionally with one last append in the same transaction. `abcp_publisher_abandon_v1` locks both, validates `PublisherRecoveryProofV1` against the owner reservation/lease and exact process/container absence, proves no later ordinal than the proof, and CASes ACTIVE→ABANDONED. Exact replay returns the existing same terminal record; conflicting replay fails.

`abcp_close_stage_v1` locks the stage row, reads publishers in publisher-id order without waiting indefinitely, and either (a) returns at most 256 exact ACTIVE IDs with no state change so the controller can publish recovery proofs and call abandon, or (b) when zero ACTIVE remain, changes OPEN→CLOSED and returns cutoff `next_occurrence_ordinal-1` at commit. The controller performs at most one recovery attempt per returned ACTIVE row per close invocation; unresolved owner/absence proof yields `RECOVERY_HOLD`/stage failure, never an unbounded wait or forced close. Because every append/finalize/abandon reacquires the stage lock and rechecks OPEN, no late occurrence can pass a concurrent close. PostgreSQL identity allocation is not used as ordering. Application independently hashes loaded state/blob/occurrence bytes. Commit ambiguity is fresh-connection exact row/revision read-back only.

Connection bounds remain connect 5s, operation/transaction 15s, lock 2s, statement 10s, idle-in-transaction 15s, pool MaxConns4/Min0/lifetime30m/idle5m/health30s. Harness is loopback SCRAM with `sslmode=disable`; non-loopback operator DB requires `verify-full` + CA/hostname. The exact PostgreSQL image remains `postgres@sha256:f3bd19c606e442c3d7bdfa8002e03fe260a1023351e0ea4598032022b68dd6e3` linux/amd64 17.6-bookworm.

## Evidence and secret inventory authority

Every attempt first commits the shared `WorkerCapacityReservationV1` and workflow `AssuranceResourceReservationV1`, then calls the locked publisher-open operation. Execution emits its identity/evidence/resource blobs and publishes a distinct occurrence for every retained PASS/FAIL/VALIDATION_UNAVAILABLE/unselected/orphan stage artifact—even when two occurrences reuse identical bytes. The stage/subject row, not a global sequence, assigns contiguous commit-ordered ordinals. Every ACTIVE publisher must reach FINALIZED or exact-proof ABANDONED before close; close returns bounded recovery work and fixes the cutoff only after none remain. The controller reads exactly ordinal `1..cutoff`, rejects gaps/duplicates, builds at most 16 pages of at most 128 entries, verifies the domain-separated Merkle root, and thus covers the full 2,048-occurrence ceiling.

Inventory pages/manifest, scan authority/evidence and `StageClosureV1` are generated only after the occurrence set is CLOSED. They are immutable closure blobs, not members of the occurrence set they describe. The inventory manifest enumerates its pages, the scan authority enumerates the manifest/pages as `closure_metadata_sha256s`, and the final closure enumerates those records while excluding its own digest. This exact layering removes self-reference; only OPEN-stage retained artifacts are claimed as complete occurrences. Unreferenced blobs have no stage occurrence and cannot satisfy evidence, while a blob from an abandoned attempt still has its explicit ORPHAN occurrence if it was retained before close.

The controller registers every acquired/generated credential under `(lineage,stage,stage_subject,secret_id,capability,acquisition identity)` before its first use. `StageSecretSetV1` is controller-owned; each `value_commitment_sha256` is SHA-256 of `"ABCP-SECRET-V1" NUL commitment_nonce NUL secret_id NUL decimal_length NUL exact_secret_bytes`. Before execution, it derives `StageDiffLineageV1` from the stage rule and seals `StageSubjectV1.diff_base_oid/diff_candidate_oid`; B uses active B-grant base→B candidate, C uses its transitively preserved base→unchanged C candidate, integration uses integration baseline→integrated head, and post-merge uses premerge base→merge result. No caller supplies either OID independently.

At closure, after ordinary publishers finalize, the controller seals the complete secret set, re-derives the same lineage pair, and obtains candidate diff bytes in quarantine. `CandidateDiffArtifactV1`, its occurrence, `SecretScanAuthorityV1`, `SecretScanEvidenceV2`, and the inventory entry all repeat exact subject/lineage/base/candidate/diff digest equality. The command is exactly `LC_ALL=C git diff --binary --full-index --no-ext-diff --no-textconv <authorized-base> <authorized-candidate> --`; missing objects, stderr, nonzero exit, pair mismatch or byte/digest mismatch fails. Only a preliminary full-set zero match allows the final publisher to commit the diff occurrence and finalize; a match retains only digest/size incident metadata and the stage fails without PASS. The stage then closes, and the final scan streams every sealed occurrence blob exactly once, including that exact diff occurrence. The scanner receives the complete secret values and nonce over controller FD3, recomputes commitment/count, and fails if they differ. Empty, unrelated, reversed, stale-base, stale-candidate and correct-bytes/wrong-pair rejection vectors are mandatory. A positive match or any missing credential/diff/blob/page/count/pair prevents PASS and stores only redacted `SecretEgressIncidentV1`; offending raw bytes/raw output are never inserted.

Real upstream provider credentials never enter the Codex process, repository, child environment, argv, config file or evidence. J-05 starts a controller-owned loopback-only `CodexProviderBrokerV1` whose entire provider contract is the canonical `CODEX_BROKER_V1` vector: derived base URL `http://127.0.0.1:<reservation-owned-port>/v1`; only `POST /responses` and `POST /responses/compact`; 900,000 ms token TTL, at most five renewals, 32 requests/token and 128/session, 8 MiB aggregate request and 256 MiB response bytes; connect/request/stream-idle/session timeouts 5,000/300,000/60,000/5,400,000 ms; zero transport retry and zero stream reconnect. Codex 0.149.0 uses `model_provider="abcp-broker"`, `env_key="ABCP_BROKER_SESSION_TOKEN"`, `wire_api="responses"`, `requires_openai_auth=false`. Each 256-bit session token is bound to exact reservation/execution/tool/model/budgets; renewal atomically invalidates the old token. `shell_environment_policy.exclude=["ABCP_BROKER_SESSION_TOKEN"]` is mandatory.

Before any real broker session, the exact Codex sandbox/config runs harmless-sentinel probes proving (a) token-name absence from tool-shell environment, (b) a tool subprocess cannot read a same-shaped marker from the Codex parent environment/proc view, and (c) a tool subprocess cannot connect to the broker loopback endpoint while the Codex client can. Any readable marker, reachable tool connection, inability to prove the parent-process boundary, provider/config/route drift or probe ambiguity is `VALIDATION_UNAVAILABLE`; no real provider credential/session starts. The broker rejects non-loopback clients, wrong/expired/replayed tokens, unbound models, budget overflow and non-allowlisted routes; strips inbound authorization before injecting upstream credentials; never follows redirects or uses proxies; closes a stream at idle/total timeout; and never logs credential/token/header/body bytes.

PostgreSQL/Docker passwords are controller-generated into 0400 files in an ephemeral 0700 directory outside repo/evidence roots; Docker receives only `POSTGRES_PASSWORD_FILE=/run/secrets/postgres_password` and a read-only bind of that file. Secret-capable process raw stdout/stderr is scanned in bounded memory and discarded; only structured secret-free results are retained. Exact secret values (including the broker session token and upstream credential inside the controller boundary) are delivered to `assurance-secret-scan.py` over controller-owned FD3 length frames, never argv/env/file evidence.

A credential-bearing stage cannot publish its evidence-selection checkpoint until its complete inventory and matching stage-local PO-041/PO-052 zero-match scan are PASS. B, C, integration and post-merge each have such cells.

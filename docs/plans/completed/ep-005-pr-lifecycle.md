## Durable PR-resource admission and revision authority

The durable interlock is keyed by the **physical PR resource**, not by a particular payload, actor, accepted head SHA, run, limits profile, or filesystem path. `PRResourceKeyV1` is the SHA-256 of the versioned canonical tuple `(repository owner, repository name, base branch, head repository owner, head repository name, head branch)`. This one key owns discovery/create/update serialization for that base/head PR relationship across head-SHA changes, actor changes, title/body changes, retries, process restarts, and governed runs. CREATE and UPDATE are modes beneath the same resource; operation kind is therefore not part of the resource key.

Each requested metadata state is a resource-owned immutable `PRRevision`: monotonically increasing revision ordinal, exact full source/derived Authority bytes and digest, exact accepted head SHA, stable acting-principal identity, canonical desired title/body bytes and digest, frozen production-limits identity, admission-policy identity, resolved CREATE/UPDATE mode and exact PR identity when UPDATE, plus the preflight proof digests that admitted the revision. Exactly one revision may be active for a physical resource. A different actor/document/head-SHA request cannot create a parallel revision while an active revision has a generation or any submitted/ambiguous history. If an active revision has **no generation record at all**, the controller may supersede it only under the resource lock by durably recording `superseded_zero_write` after proving no generation/marker exists; otherwise it must be resumed or fail closed. A clean non-ambiguous `applied_confirmed` revision may admit a later revision only after fresh read-only proof that the remote PR still has the same terminal-bound PR number/node ID, repository/base/head repository+branch identity, and exact prior title/body, with no unresolved or ambiguous-history barrier. The head SHA is allowed to advance only to the new Authority's exact `HeadSHA` and must be re-proved by the dedicated head-ref + full-PR observations; the base tip is re-proved against the new Authority. Thus a legitimate later revision can follow a clean head advance without treating the old head SHA as current. An `applied_reconciled` revision reached after an ambiguous write is terminal for replay but sets a permanent `ambiguous_history` barrier for this track: no later metadata revision is authorized because GitHub cannot prove the earlier request has no delayed side effect. Removing that barrier requires a separately designed future recovery authority. Thus a delayed old PATCH can never race a newer revision.

The desired title/body for a revision are persisted byte-for-byte before submission and are never regenerated. Clock-derived text, random/run IDs, ephemeral paths, mutable evidence URIs, or other restart-variant material are forbidden. The resource key and revision identity are recomputed from persisted records on every open; mismatch is integrity failure. Policy/limits changes cannot re-key the physical resource. An incompatible stored admission policy or production-limits identity is `ADMISSION_POLICY_MISMATCH` and fails closed pending an explicitly designed migration.

Use one controller-owned durable `PRWriteAdmissionStore` outside run-scoped evidence. Its production root is an absolute, controller-configured stable host path, not a plan/task/run input; tests may inject an isolated root only through a test boundary. The root must pre-exist with mode 0700, remain the same opened directory device/inode for the process lifetime, reject symlinks/special files, and use a flat fixed-name layout. No per-resource subdirectories, fallback roots, automatic deletion, or retention compaction are allowed in this task.

Two lock classes govern the flat store. The administrator-provisioned store root already contains a regular mode-0600 `capacity.lock`; the lifecycle never creates or replaces that bootstrap lock. The root-wide `capacity.lock` serializes global capacity accounting and every file-creating/replacing mutation. It is opened with no-follow/same-inode checks and its device/inode identity is fixed for the process lifetime just like the root. A per-resource `flock(LOCK_EX|LOCK_NB)` serializes one physical PR resource across processes; in-process keyed mutex serialization is also required. Initial resource-lock-file creation acquires `capacity.lock` first, proves projected capacity, creates/fsyncs the lock file, fsyncs the root, releases `capacity.lock`, and only then acquires the resource lock. After a resource lock is held, later store mutations acquire locks only in `resource -> capacity` order; no code path may acquire them in reverse. Lock descriptors are dedicated and never duplicated/shared. Unsupported or uncertain lock semantics fail closed; generic POSIX process record locks are forbidden. Kernel release of `flock` on process exit/crash is the sole live-owner liveness assumption.

`PRAdmissionPolicyV1` fixes `MaxAdmissionResources=4096`, `MaxAdmissionFiles=65536`, and `MaxAdmissionBytes=512 MiB`. Under `capacity.lock`, before **every** store mutation—including existing-resource generations, markers, reconciliation rounds, terminals, ledger-recovery records, and first lock-file creation—the controller performs a bounded inventory of all known flat-layout entries, rejects unknown/symlink/special entries, and checks projected actual files/bytes plus outstanding virtual terminal reservations. Before a submitted marker can be published, the projected accounting must reserve one future terminal file and `256 KiB` terminal bytes; the marker durably records that reservation. Outstanding reservations count against global file/byte caps until a terminal consumes them, so concurrent distinct resources cannot oversubscribe capacity. `statfs` must independently prove physical free-space headroom for the write plus all outstanding terminal reservations. Capacity failure is zero-write and fail-closed.

The production lifecycle profile is exactly `githublifecycle.DefaultLimits()` from the frozen foundation. Production callers cannot supply or relax it. The controller computes and binds its canonical SHA-256 and rejects any different profile; tests may inject only component-wise stricter limits. All page/item/text/evidence/retry/timeout, HTTP-body, generation, reconciliation, and capacity-derived calculations use this exact production profile plus the stricter fixed track caps below.

This GitHub track is intentionally stricter than the frozen generic retry allowance: **one and only one submitted generation may ever exist for a revision**. `Limits.MaxWriteRetries` remains part of the frozen `DefaultLimits()` identity but does not grant this track a second remote submission. All zero-write prerequisites—principal proof, fresh refs, exact discovery/direct selection, exact request construction, and run-scoped pre-write evidence—finish before generation allocation. Failures before the submitted marker consume no remote-submission authority; an allocated unsubmitted generation is resumed in place under the bounded resume rules below. Once its submitted marker exists, that revision has zero replay authority regardless of error classification or reconciliation disposition. A generation immutably records revision/resource identity, resolved mode/target, source/derived Authority, frozen WriteAttempt, principal/ref/selection proofs, and payload digest. Generation files use create-without-replace, file fsync, then root fsync.

Immediately before POST/PATCH, the controller publishes an immutable `submitted` marker that binds the exact generation/WriteAttempt and the exact fresh preflight bundle authorizing this submission. The marker is capacity-checked with the terminal reservation above, fsynced, and followed by root fsync; the HTTP client MUST NOT be invoked first. All request construction that can fail is complete before marker publication begins. If marker creation/file-fsync/root-fsync returns any uncertain durability error, the controller performs **no HTTP call** and returns a local admission failure, but it may not assume the marker is absent. On every restart/re-entry under the resource lock, presence of any valid submitted-marker file is conservatively treated as `submitted + unresolved` even when the prior process may have stopped before `Do`; absence may authorize resume only when the marker is securely proven absent and no prior submitted marker/terminal exists. A corrupt/partial/conflicting marker is `ADMISSION_INTEGRITY_FAILURE`, never proof of zero-write. Any error after `http.Client.Do` is invoked is `submitted=true`/ambiguous. A generation with a marker and no terminal is unresolved and blocks all revisions/new generations except read-only reconciliation of that exact attempt.

If a generation record exists but its submitted marker never became durable, it is resumed in place rather than replaced. Resume freshness uses a separate durable monotonic `resume-round` namespace (`1..4`) under the resource lock, independent of prepare rounds and `MaxReadRetries`. Each resume publishes a fresh run-scoped proof bundle and the eventual submitted marker binds that bundle. Divergence blocks without rewriting the generation. After four exhausted resume rounds, return `RESUME_BUDGET_EXHAUSTED`; the generation remains zero-write/unsubmitted, no submitted budget is consumed, and only fail/cancel or separately authorized repair may continue.

A submitted generation may terminalize only as `applied_confirmed`, `applied_reconciled`, or `remote_diverged_after_write`; `ReconciliationUnknown` is append-only observation, not terminal. The GitHub adapter in this track has no authoritative request-status/idempotency primitive, so `ReconciliationNotApplied` is not an accepted replay-enabling terminal. If such a generic frozen disposition is ever returned, the track records bounded diagnostic evidence and fails closed as `UNSUPPORTED_NOT_APPLIED_PROOF`; it does not allocate another generation. Clean later revision admission is governed only by the resource-level `applied_confirmed` rule above.

The controller derives the single generation's `writeID` from `PRResourceKeyV1 + revision ordinal + generation=1`; callers cannot supply it. UPDATE mode first derives lifecycle Authority with the exact observed PR number/node ID. CREATE uses nil PR identity. No write ID, actor, document, head SHA, limits profile, retry counter, or run packaging can create a second resource interlock.

## Authority freshness and external entry preconditions

This track does not publish Git branches and does not re-run Phase 3. Before any admission generation is created, it proves two entry conditions with fresh bounded remote reads:

1. **Remote accepted head exists.** The governed same-repository head branch must already be present on GitHub and its exact ref observation must equal `Authority.HeadSHA`. Its producer is the repository's authenticated candidate-publication/push mechanism outside this Phase-4 PR-lifecycle task. ABCP does not trust that producer's assertion; only the fresh GitHub ref proof is authoritative here. A 403/404, wrong branch, wrong object kind, or wrong SHA is the named `REMOTE_HEAD_UNPUBLISHED_OR_DIVERGED` external precondition: zero generation is created, zero write is attempted, and the same Authority may be rechecked only after the external publication condition changes. This task never silently performs a push.
2. **Phase-3 base authority is still fresh.** The live base ref must equal `Authority.ExpectedBaseTipSHA`. The frozen foundation deliberately couples that SHA to `ExpectedMergeContent.SourceBaselineSHA`; this track may not weaken it. If the base has advanced, return `STALE_READY_FOR_MERGE_AUTHORITY` with the old/new base proofs and perform zero PR writes. Because the existing run state cannot move backward from `READY_FOR_MERGE`, the stale run may only be failed/cancelled under existing state authority; continuation requires a new governed run through Phase-3 integration/combined acceptance against the current base, producing a new `READY_FOR_MERGE` decision and new lifecycle Authority.

These are explicit entry preconditions, not hidden assumptions. Head publication can be satisfied externally and rechecked under the same fresh Authority; base movement invalidates that Authority and requires re-derivation rather than retry.

## Remote observation and exact REST contract

Remote data is untrusted until validated. Track-owned immutable proof types are:

- `HTTPRequestIdentity`: canonical method, path-template identity, escaped path, canonical sorted query, API origin, API version, accept/content type, expected success status set, request-body SHA-256 when present, and bounded-response policy identity.
- `RemoteRefObservation`: request identity, echoed `ref`, object type, exact Git SHA, safe GitHub request ID, observed time, production-limits identity, canonical digest.
- `RemotePrincipalObservation`: request identity, stable numeric GitHub user `id`, `node_id`, login display text, safe request ID, observed time, canonical digest.
- `RemotePRObservation`: request identity, exact PR number/node ID, repo/base/head refs, PR-reported `head.sha`/`base.sha`, head/base repository identities, `head.label`, PR author stable numeric `id` + `node_id` + login, state, explicit merged boolean, title/body, safe request ID, observed time, limits identity, canonical digest.
- `PRDocumentObservation`: binds one validated frozen `PullRequestSnapshot` to the exact full-PR observation plus dedicated head/base ref observations and their digests.

Production GitHub REST origin is exactly `https://api.github.com`; redirects are disabled and caller-supplied URL/host/path/query/header authority is forbidden. All requests set `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2026-03-10`; JSON writes additionally set `Content-Type: application/json`. The sealed authenticated transport alone injects Authorization. The client has no application response cache and sends no conditional request headers; `304` is never success. Path components are escaped segment-by-segment from already validated identities and queries are built from fixed keys with `url.Values`, never string concatenation.

The complete allowed request matrix is frozen:

| Purpose | Method/path/query | Request body | Only success status |
| --- | --- | --- | --- |
| acting user | `GET /user` | none | `200` |
| exact ref | `GET /repos/{owner}/{repo}/git/ref/heads/{branch}` | none | `200` |
| filtered PR discovery | `GET /repos/{owner}/{repo}/pulls?state=open&head={owner}:{head}&base={base}&sort=created&direction=asc&per_page={MaxItemsPerPage}&page=1` | none | `200` |
| exact PR | `GET /repos/{owner}/{repo}/pulls/{number}` | none | `200` |
| CREATE | `POST /repos/{owner}/{repo}/pulls` | exactly `title`, `body`, `head={owner}:{head}`, `base={base}` | `201` |
| UPDATE | `PATCH /repos/{owner}/{repo}/pulls/{number}` | exactly `title`, `body` | `200` |

No other PR mutation fields (`state`, `base`, `maintainer_can_modify`, draft transition, merge fields) are emitted. Non-success codes are classified but never accepted as result evidence. A write-side `422`, 5xx, timeout, cancellation, EOF, or malformed/oversized response after `Do` begins remains ambiguous/submitted and is reconciled read-only.

Numeric transport caps are fixed before decode: request JSON `<= 16 KiB`; successful or error response body `<= 4 MiB`; the underlying `http.Transport.MaxResponseHeaderBytes` is fixed to `32 KiB` and the adapter also bounds the headers it canonicalizes to that same cumulative limit; `Link` header `<= 8 KiB`; safe `X-GitHub-Request-Id` `<= 256` bytes. Over-limit data fails closed; raw error bodies and secret-bearing headers are never persisted. Bodies are always closed and bounded readers are used before JSON decode.

Field provenance is fixed: PR identity/state/document/repositories/refs/author come only from the full single-PR response; exact current head/base tip SHAs come only from dedicated ref reads. List responses are enumeration evidence only. PR-reported `head.sha` must equal the dedicated head-ref observation; PR `base.sha` is metadata and never substitutes for the dedicated current base-ref proof. No remote-observation field is populated from Authority. The frozen snapshot's composite `SnapshotIdentity.RequestID` is derived deterministically from canonical component-observation digests.

For this PR-metadata track, the frozen `PullRequestSnapshot` is deliberately a minimal identity snapshot: `Reviews` is empty, `EvidenceRefs` is empty, and `Metadata` is empty. Title/body, author, head repository/label and request provenance live in the track-owned bounded observations rather than being duplicated into generic snapshot metadata. This fixed profile keeps the snapshot/recovery wire small and prevents unrelated review/metadata fan-out from entering the PR-write terminal. The complete final terminal is hard-bounded to `256 KiB`. Because postflight bytes do not exist before submission, pre-submit admission does **not** pretend to construct the final terminal. Instead `TerminalBudgetV1` proves a deterministic worst-case bound from the actual pre-write Authority/document bytes plus fixed track maxima for every future normalized wire: each Authority canonical form `<=32 KiB`; WriteAttempt `<=8 KiB`; snapshot canonical+recovery material `<=32 KiB`; principal observation `<=8 KiB`; full-PR observation `<=32 KiB`; both ref observations together `<=16 KiB`; one applied-reconciliation observation `<=32 KiB`; result-core material `<=16 KiB`; all remaining schema/reason/evidence-name/event overhead `<=32 KiB`. The sum must be `<=256 KiB` before the submitted marker consumes its 256-KiB terminal reservation, and final canonical terminal bytes are checked again against the same cap before publication. A wire exceeding its individual cap is invalid remote/local evidence and can never consume the reserved terminal through silent growth.

For exact refs, require echoed `ref == refs/heads/<exact branch>` byte-for-byte, `object.type == "commit"`, one object rather than an array/prefix response, and a complete lowercase SHA accepted by `NewGitSHA`.

## Provider / authenticated principal boundary

Credentials remain only inside the sealed transport and never enter Authority, plans, canonical evidence, errors, admission records, or ledger material. This track supports `ActingKindUser` only. For this track, the frozen generic `ActingIdentity.Subject()` has a stricter semantic contract: it must be exactly `github-user-id:<positive-decimal-id>`, representing GitHub's stable numeric account `id`, not mutable login text. Any other user-subject form and all `ActingKindAppInstallation` values fail closed before any write; app-installation proof remains a later track.

Before every submitted generation and every ambiguous adoption invocation, call `GET /user` through the same credential channel. Require returned numeric `id` exactly equals the Authority subject's numeric ID; require bounded nonempty `node_id` and login and persist both as corroborating provenance. On CREATE postflight/adoption, the PR author's numeric `id` and `node_id` must exactly equal the freshly observed authenticated user; login is retained as display provenance but is not the security identity. No constructor accepts arbitrary `(actor, token)` as proof.

## Exact open-PR selection

Use one track-owned exact-open eligibility predicate for both discovery and Authority-bound direct lookup. An eligible PR must have `state == open`, `merged == false`, exact repository identity, exact base repository, exact head repository, exact base ref, exact head ref, exact `head.label`, exact PR-reported head SHA equal to the dedicated head-ref observation, and exact governed head/base ref observations.

For Authority already binding a PR, GET exactly that PR number; HTTP 403/404 or any inability to prove it is fail-closed. Require the exact node ID and run the response through the same exact-open eligibility predicate, then pass its frozen snapshot through `SelectPullRequest` for re-proof before deriving the update Authority. Do not treat a bound PR as trusted merely because its number/node ID matches.

For unbound Authority, discovery MUST use GitHub's authority-bound server filters rather than scanning the repository's global open-PR list: fixed `state=open`, exact `base=<base-branch>`, exact `head=<owner>:<head-branch>`, stable `sort=created`, stable `direction=asc`, bounded `per_page`, and `page=1`. The list response is candidate/enumeration evidence only; it is never itself a complete `RemotePRObservation`. Those parameters are derived only from validated Authority; callers cannot inject arbitrary query text. The adapter inspects the pagination `Link` header only as bounded metadata and never follows its URL directly. Absence of `rel="next"` is the required end-of-results proof for the filtered result set. Presence of `rel="next"`, malformed/oversized Link metadata, or a result set exceeding the bounded page is `DISCOVERY_TRUNCATED` and fails closed; it is never interpreted as zero matches. This avoids correctness depending on mutable offset pagination across an unrelated busy repository.

Every returned list item is independently decoded and bounded and the raw candidate list is preserved as evidence. Mode resolution is based first on the **raw complete filtered item count**, never on incomplete list-item fields:

- raw filtered item count = 0 → resolve CREATE;
- raw filtered item count = 1 → GET that exact returned PR number through the full single-PR endpoint, require its node ID agrees with the list candidate, build the complete `RemotePRObservation` only from that GET plus dedicated ref reads, then run the exact-open eligibility predicate and `SelectPullRequest`; if all pass, derive Authority with exact PR identity and resolve UPDATE;
- raw filtered item count = 1 but the full GET is missing, identity-mismatched, or fails any exact-open predicate → `EXISTING_INELIGIBLE_OPEN_PR`, zero generation and zero write; recheck read-only only after the remote condition changes;
- raw filtered item count > 1 → ambiguity failure before any mode choice, regardless of which list summaries appear eligible.

A frozen `PullRequestPage.total` is the exact raw observed count on that filtered page, never a fabricated repository-global total. Thus a stale/eventually-consistent PR object is never converted into evidence of absence. HTTP 422 from a true race after a zero-item proof is classified as submitted/ambiguous and goes through the exact reconciliation path below, never an automatic retry.

## Exact write and CAS-race handling

Before every POST/PATCH generation, freshly read governed head and base refs and require exact equality with Authority head/base SHAs. Create submits exact base/head/title/body; update changes only title/body on the exact derived PR Authority and never retargets base/head.

The frozen input validator currently permits only control-character-free text; this task therefore intentionally supports bounded single-line title/body. GitHub `body:null` or absent body is normalized to `""` only on response decode; submitted canonical payload bytes and WriteAttempt digest are never rewritten.

After the write, immediately GET the exact PR and re-read both refs. Build a fresh `PRDocumentObservation` and re-run the same exact-open eligibility proof used at preflight: require `state == open`, `merged == false`, exact PR number/node ID, exact base/head repositories, exact base/head refs, exact `head.label`, exact PR-reported head SHA, and dedicated head/base ref proofs all equal the accepted derived Authority. Also require title/body exact equality to the submitted document. GitHub offers no atomic expected-head CAS for PR metadata writes. If the head/base moves, the PR is closed or merged, repository/ref/head-label identity diverges, or any other exact-open identity proof fails between preflight and postflight, the remote mutation may have happened but success is forbidden: terminalize the admission generation as `applied` with reason `remote_diverged_after_write`, return an attempt-bound submitted error/unresolved governance result, and never retry. This rule applies even when the PATCH/POST itself returned success.

Every provider error after the HTTP client is invoked for POST/PATCH is represented with the exact frozen WriteAttempt and `submitted=true`. Provider/substantive error helpers that lose attempt/submission provenance are forbidden for this path. HTTP 422 duplicate/race responses are reconciled by reads and are never treated as proof of `not_submitted`.

## Ambiguous outcome and reconciliation

Lost response, timeout, cancellation, EOF, malformed/oversized success body, 5xx after submission, response-parse failure, or HTTP 422 after the HTTP client was invoked is an ambiguous submitted outcome carrying the exact frozen WriteAttempt. The generation remains `submitted` with no terminal record while reconciliation runs. Reconciliation is always read-only and authority/attempt-bound.

Construct `NewReconcileWriteInput` from the exact attempt and accept a provider reconciliation result only when its attempt/limits/evidence revalidate exactly. Then apply these stricter track rules:

- **Applied.** Fresh exact discovery/direct GET plus fresh head/base refs must prove the same full postflight predicate and exact desired title/body under the original source/derived Authority. The adopting invocation repeats `GET /user` through the same credential channel and requires the stable numeric GitHub account ID to equal `Authority.Actor().Subject()` under this track's `github-user-id:<id>` rule. For CREATE, the adopted PR author's numeric account ID and node ID must equal that freshly observed principal. Publish bounded reconciliation evidence, construct/validate the frozen `PullRequestWriteResult`, and persist an `applied_reconciled` terminal. This returns verified success for the current revision but permanently sets the physical resource's `ambiguous_history` barrier; later metadata revisions remain forbidden in this track.
- **Not applied.** The GitHub adapter does **not** manufacture `ReconciliationNotApplied` after a submitted POST/PATCH because this design has no authoritative GitHub request-status/idempotency proof. Mere PR absence, unchanged mutable fields, elapsed time, 404, or a filtered zero-result response is never proof. Even if the generic frozen provider boundary unexpectedly returns `ReconciliationNotApplied`, this stricter track grants **no replay authority**: persist bounded diagnostic evidence, leave the one submitted generation permanently non-replayable, and return `UNSUPPORTED_NOT_APPLIED_PROOF`. Pre-`Do` local failures are handled before durable submission by resuming the same unsubmitted generation and never need a second generation.
- **Unknown.** Persist only the next permitted bounded reconciliation round and leave the generation submitted/unresolved. It blocks every new generation and every new resource revision. A later invocation may reacquire the same physical-resource lock and perform another bounded read-only reconciliation of the exact attempt. Unknown can never authorize replay, a second generation, or a later resource revision.

This preserves and tightens the frozen foundation's safety/liveness trade-off: ambiguous writes have zero implicit retry authority. `MaxWriteRetries` remains evidence-bound as part of `DefaultLimits()` but is not consumed as an operational replay budget by this track; pre-submission local/read/evidence failures resume the same zero-write generation, and every post-marker outcome has zero remote replay authority.

Neither `CanRetry` nor provider reconciliation is independent authority. This track never calls a second remote PR submission after a submitted marker, even if generic `CanRetry` would return true. `applied_confirmed` and `applied_reconciled` both forbid replay of their revision; only `applied_confirmed` may later permit a **new revision**, and only under the fresh physical-resource proof and no-barrier rules above.

## Evidence, reconciliation, terminal recovery, and cleanup

Before remote-generation allocation, publish-or-verify preflight/principal/selection evidence under a bounded monotonic `prepare-round` ordinal (`1..MaxReadRetries+1`) in the current controller run-evidence root. Names are controller run ID + resource key + revision ordinal + prepare round + phase. The controller securely discovers the highest existing round after restart and never resets it in that governed run. Existing artifact name is success only when bounded-read bytes exactly equal intended bytes; mismatch is integrity failure. Prepare-round exhaustion is a zero-write preflight failure and consumes no submitted budget. Resume rounds use the separate durable `1..4` namespace defined above.

Repeated reconciliation uses a monotonic `reconcile-round` under the resource lock. `PRReconciliationPolicyV1` allows at most 8 persisted rounds per submitted generation, at most `8 * Limits.MaxTextBytes` bytes per round, at most `64 * Limits.MaxTextBytes` aggregate reconciliation bytes, and at least 30 seconds between persisted rounds. Names include resource key + revision + generation + reconciliation round + phase. Before every append, root-wide capacity accounting and `statfs` headroom checks run. At/beyond count/byte/rate/capacity limits, no write is authorized; return `RECONCILIATION_BUDGET_EXHAUSTED` with the submitted generation unresolved. A later controller-authorized diagnostic read may inspect remotely but may not mutate admission evidence or authorize a write.

Ambiguous reconciliation remains attempt-bound. `ReconciliationApplied` requires the same full postflight predicate, fresh authenticated-principal proof, exact desired document, and one track-owned bounded reconciliation evidence artifact; CREATE additionally requires stable PR-author account ID/node ID equality. It terminalizes as `applied_reconciled`, returns verified success for this revision, and sets the resource `ambiguous_history` barrier that forbids later revisions in this track. `ReconciliationUnknown` appends only the next bounded observation. `ReconciliationNotApplied` is deliberately unsupported by this GitHub track and never terminalizes into retry authority: absence/404/unchanged state are not proof, and even an unexpected generic not-applied disposition is recorded only as bounded diagnostic evidence before `UNSUPPORTED_NOT_APPLIED_PROOF` blocks the revision permanently.

### Durable material result and restart recovery

The durable result material is split to avoid a hash cycle. `PRLifecycleResultCoreV1` is a track-owned immutable canonical value containing only data known before the final terminal digest: disposition (`applied_confirmed`, `applied_reconciled`, or `remote_diverged_after_write`), physical resource key, revision/generation/write ID, exact repository/base/head branch identities, accepted head SHA and expected base-tip SHA, exact PR number/node ID when known, desired title/body digest, stable acting-principal numeric GitHub ID plus node ID/login provenance, exact validated snapshot digest, and exact postflight/ref/reconciliation observation digests. It contains **no final terminal digest, material-event digest, or evidence reference that depends on terminal publication**. The public `PRLifecycleResultV1` is constructed only after final terminal publication as `{core, terminal_digest, immutable_evidence_refs}`. Later Phase-4 tracks consume that wrapper; the terminal itself embeds only `PRLifecycleResultCoreV1`, so result identity cannot be circular.

On the **live** successful path, while the original frozen `Authority` still exists in memory, the controller constructs `UpsertPullRequestInput`, validates the provider response with `NewPullRequestWriteResult` + `ValidatePullRequestWriteResult`, validates the track-owned full postflight/principal/ref predicate, and only then converts that accepted material into `PRLifecycleResultCoreV1`. That core conversion is deterministic and is itself validated against the live Authority, WriteAttempt, exact desired document, production limits, and remote observations before terminal publication. After the final terminal is durably published, the controller constructs the public `PRLifecycleResultV1` wrapper from the validated core + final terminal digest + immutable evidence refs.

A terminal is the self-contained durable recovery authority for that track-owned result core. It is `<= 256 KiB` and binds: schema/admission-policy/production-limits identities; resource key + revision + generation; generation-record and submitted-marker digests; exact WriteAttempt **canonical bytes and parsed primitive fields**; exact source/derived Authority canonical bytes + SHA-256 **for identity verification only, never rehydration**; a bounded mirrored authority wire containing repository/base/head branches, accepted head SHA, expected base-tip SHA, actor kind/subject, optional PR number/node ID, allowed merge method and ExpectedMergeContent SHA-256; desired title/body bytes + digest; exact validated `PullRequestSnapshot` canonical bytes/digest **plus a primitive snapshot recovery wire** sufficient to rebuild the snapshot via public constructors; canonical bytes/digests of the track-owned principal/full-PR/head-ref/base-ref/reconciliation observations needed by the disposition; resulting `PRLifecycleResultCoreV1` canonical bytes/digest when success is reportable; terminal reason/failure classification; originating run ID; terminal timestamp; intended run-evidence artifact names/digests; and deterministic material-ledger-event canonical bytes/digest.

The primitive recovery wire never claims it can recreate opaque foundation authority. Repository, branch, Git SHA, PR identity and snapshot identity values are persisted as strings/integers and reconstructed only through the frozen public constructors (`NewRepository`, `NewBranch`, `NewGitSHA`, `NewPullRequestIdentity`, `NewSnapshotIdentity`, `NewPullRequestSnapshot`). The terminal must strictly decode the stored canonical Authority JSON into a track-owned mirror schema with unknown fields rejected, require canonical re-encoding byte-for-byte equals the stored Authority bytes, recompute its SHA-256, and prove every mirrored authority field agrees with the generation/WriteAttempt identities created on the live path. The nested `expected_merge_content` is retained as bounded `json.RawMessage` plus SHA-256 and cross-checked with the mirrored expected-content digest recorded live; it is never instantiated as the opaque Go type. Because `ExpectedMergeContent` has no public rehydration constructor, restart **must not** call `NewAuthority`, `DeriveExpectedMergeContent`, `NewUpsertPullRequestInput`, `NewPullRequestWriteResult`, or any other API that would require recreating the opaque authority. A mismatch between canonical Authority bytes/digest, mirrored fields, WriteAttempt authority digest, snapshot wire/canonical digest, track observation digests, or result wire is `ADMISSION_INTEGRITY_FAILURE`.

On restart, after acquiring the physical-resource lock, the controller bounded-reads and validates the terminal and all admission records before any remote request. It reconstructs the `PullRequestSnapshot` from the primitive recovery wire and requires its canonical JSON/SHA-256 to exactly equal the stored snapshot bytes/digest under production limits. It independently validates the track-owned remote observation wires and the stored `PRLifecycleResultCoreV1`. This proves recovery of the already-validated live outcome without inventing a frozen Authority. A valid `applied_confirmed` or `applied_reconciled` terminal reconstructs the identical public `PRLifecycleResultV1` from `{stored core, validated final terminal digest, republished immutable evidence refs}` and performs no GitHub call; reconciled success preserves the permanent ambiguous-history barrier. A `remote_diverged_after_write` terminal reconstructs the same unresolved governance result and never retries. A later **new** clean revision obtains a fresh live Authority through the normal Phase-3-derived path and proves it against the prior `applied_confirmed` terminal; the terminal itself is never used to manufacture that Authority.

### Deterministic material ledger recovery

Terminal/event hashing is explicitly non-circular. First construct `TerminalCoreV1`, which contains every terminal field **except** material-ledger event bytes/digest and final terminal digest, and compute `terminal_core_digest`. The deterministic event uses `SchemaVersion=ledger.CurrentSchemaVersion`, `EventID = sha256("pr-lifecycle-terminal-event-v1" || terminal_core_digest)`, the core's originating run ID and timestamp, fixed actor/source/type, no domain state transition fields, and a bounded payload binding `terminal_core_digest` + resource/revision/generation/attempt/disposition. Construct it directly, call `Event.Validate()`, and JSON-canonicalize it. Then construct the final terminal by embedding `terminal_core_digest` plus exact event canonical bytes/digest and compute the final terminal digest. Neither hash depends on itself. Frozen `ledger.NewEvent` is not used because it generates random identity/time.

The frozen `JSONLLedger.Append` remains unchanged for existing control-plane writers, but material-event recovery does **not** use a separately supplied path plus opaque append interface. Production wiring gives the track-owned `MaterialLedgerRecorder` the exact canonical ledger path already selected by the controller; when a `*ledger.JSONLLedger` is also supplied, its `Path()` must byte-for-byte equal that canonical path or construction fails. The recorder resolves a controller-owned parent directory that is non-symlink, owned by the effective controller UID, and not group/world-writable, then opens the ledger itself with no-follow regular-file checks and `O_APPEND` so scan and append use the **same verified file descriptor/inode**. `ENOENT` is a clean empty-ledger observation only after the exact safe parent is proven; creation uses no-follow/exclusive-safe semantics inside that parent and the created file must be mode 0600. The recorder never follows a later path replacement after obtaining the verified descriptor.

Under the physical-resource lock, the recorder snapshots the verified descriptor's current size, rejects size above `64 MiB`, bounded-reads exactly that snapshotted prefix, requires every snapshotted record to be newline-terminated JSON with maximum line size `256 KiB`, and scans at most `262144` lines. Concurrent unrelated later appends beyond the snapshotted size are irrelevant. If the deterministic EventID exists with byte-identical canonical event JSON, publication is already satisfied. If the same EventID exists with different bytes, return `LEDGER_INTEGRITY_FAILURE`. If absent from a clean bounded snapshot, append the exact canonical event as **one bounded write on that same `O_APPEND` descriptor**, verify the full byte count, and `fsync` that descriptor before reporting success. This narrow track-owned append path intentionally reuses the existing JSONL event format and `ledger.Event.Validate()` but avoids the frozen path-reopen TOCTOU; it does not alter `internal/ledger` or domain semantics.

If the same-descriptor append or fsync returns an error after bytes may have reached the ledger, the terminal remains authoritative and **no remote write or second material event is immediately attempted**. A later recovery reacquires the same physical-resource lock, safely opens the then-current canonical ledger file, and repeats the bounded snapshot scan: exact event present is success; absent after a clean snapshot permits one append attempt; conflict/oversize/malformed/non-regular/inaccessible/unsafe-parent ledger returns `LEDGER_RECOVERY_UNAVAILABLE` or `LEDGER_INTEGRITY_FAILURE` and leaves remote replay forbidden. The same physical-resource lock serializes all recoverers for one deterministic event; unrelated writers may append different events concurrently because each JSONL event is emitted as one bounded `O_APPEND` write. Exact duplicate EventIDs are therefore not intentionally appended.

Run-scoped evidence is recovered similarly from the terminal's self-contained canonical track wires using the existing immutable publish-or-verify artifact rule. A crash after terminal fsync but before evidence/ledger/return can therefore reconstruct local material deterministically without GitHub or opaque-authority rehydration. If terminal persistence itself fails after submission, the submitted/no-terminal marker remains the safety interlock and only bounded read-only reconciliation is allowed. Raw bodies, credentials and secret-bearing headers are never terminal or ledger material.

Cleanup is non-destructive in this track: success, validation failure, cancellation, timeout, evidence failure, and reconciliation exhaustion do not delete resource/generation/marker/terminal records. Temporary files used for atomic publication are created only under the stable root, bounded, fsynced, renamed without replacement where required, and on startup are treated as untrusted leftovers; they may be removed only when no final record references them and while the appropriate resource/capacity locks are held. Cleanup failure is evidence-bearing but never authorizes replay.

## State / failure matrix

This task consumes `READY_FOR_MERGE` authority but owns no domain lifecycle transition. The admission store and ledger still form a durable side-effect state machine:

| Failure / observation | Last durable admission/evidence state | Next permitted action / required evidence |
| --- | --- | --- |
| resource lock held | unchanged | bounded recheck after owner exit; no inspect-to-mutate/write |
| capacity/policy/limits/root identity unsafe | unchanged/no new record | `ADMISSION_POLICY_MISMATCH` / `ADMISSION_CAPACITY_EXHAUSTED`; repair/migrate under separate authority; zero write |
| remote head missing/wrong or base stale | no submitted generation | head may be rechecked after external publication; stale base invalidates run authority and requires fail/cancel + new Phase-3 governed run |
| existing filtered PR candidate is ineligible/ambiguous | no submitted generation | `EXISTING_INELIGIBLE_OPEN_PR` / ambiguity evidence; read-only recheck after remote condition changes |
| preflight/principal/request/evidence failure | no submitted generation | next bounded prepare round only; after exhaustion zero-write failure |
| different request meets active revision | if active revision has no generation, durably record `superseded_zero_write`; if any generation exists, state is unchanged | only zero-write/no-generation revision may be superseded under resource+capacity locks; otherwise `REVISION_CONFLICT`, no new revision/write |
| allocated generation not submitted; storage/resume failure | same immutable unsubmitted generation | bounded resume round with fresh exact proof; after 4 rounds `RESUME_BUDGET_EXHAUSTED`, no write |
| submitted-marker publication uncertain before `Do` | marker present/partial/uncertain; HTTP definitely not invoked by current process | valid marker presence is conservatively submitted+unresolved; corrupt/partial is integrity failure; no resume/new write based on assumed absence |
| POST/PATCH possibly submitted | submitted marker + terminal reservation | bounded read-only reconciliation of exact attempt only |
| reconciliation unknown | submitted + reconciliation observations | next bounded/rate-limited reconciliation; at limit `RECONCILIATION_BUDGET_EXHAUSTED`; fail/cancel allowed, no replay |
| generic reconciliation reports not-applied | submitted generation remains permanently non-replayable | `UNSUPPORTED_NOT_APPLIED_PROOF`; bounded diagnostic evidence only; no second generation/write |
| normal response + exact postflight success | `applied_confirmed` terminal + ledger event | idempotent success recovery; later revision only after fresh prior-terminal equality and no barrier |
| ambiguous reconciliation proves exact applied | `applied_reconciled` terminal + ledger event + ambiguous-history barrier | idempotent success recovery for this revision; no later metadata revision in this track |
| write happened but postflight diverged/closed/merged/moved | `remote_diverged_after_write` terminal + ledger event | reconstruct unresolved outcome; no retry/revision |
| terminal cannot be durably written | submitted/no-terminal remains | catastrophic read-only reconciliation/recovery only |
| terminal/evidence corrupt or conflicting | integrity blocker | `ADMISSION_INTEGRITY_FAILURE`; no write; fail/cancel or separately authorized repair |
| run evidence/material-ledger publication missing after valid terminal | terminal remains authoritative | reconstruct `PRLifecycleResultV1`, publish-or-verify evidence and bounded-scan/append deterministic material event; no GitHub call |
| material-ledger scan/append ambiguous, malformed, oversized, inaccessible, or conflicting | valid terminal remains authoritative | `LEDGER_RECOVERY_UNAVAILABLE` / `LEDGER_INTEGRITY_FAILURE`; no remote write; later bounded local recovery only |

`MERGED` and production transitions remain forbidden. Returning an error never grants retry by itself.
